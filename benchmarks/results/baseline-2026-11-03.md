# Ombi SQLite benchmark results

Run: 2026-11-04 04:07:22 UTC. Host: Ubuntu 24.04.5 LTS, X64, .NET 8.0.33. Iterations: 3 per scenario (warmup discarded, median reported).

Pattern scenarios (availability, whole-graph-update, refresh-metadata, lookup) run under the current baseline SQLite configuration (DELETE journal, busy_timeout 0) so the pattern effect is measured separately from the configuration effect. Only `contention` compares configurations.

Absolute milliseconds on this host are inflated by slow fsync (each SQLite transaction commit costs ~80 ms on this VM's disk); the ratios between variants and the busy counts are the signal, not the absolute numbers. `Rows written` is the sum of EF Core SaveChanges return values: for whole-graph-update it shows how many rows a one-field change rewrites.

## Reading the pairs

- **availability**: per-item SaveChanges (current Plex shape) 129135.8 ms, 1500 rows -> one SaveChanges at end 112.1 ms, 500 rows (1152.3x). Per-item SaveChanges is the current PlexAvailabilityChecker shape; the batched variant is the Emby/Jellyfin shape (mutate in loop, one save at end).
- **whole-graph-update**: Db.Update(detached graph) (current) 1711.5 ms, 1120 rows -> stub + IsModified on one property 1667.3 ms, 20 rows (1.0x). Db.Update on a loaded TV graph is what TvRequestRepository.Update does today; the stub variant marks only the changed property, as MarkAsAvailable already does in-repo.
- **refresh-metadata**: SaveChanges per item (current) 41891.4 ms, 500 rows -> one SaveChanges at end 97.1 ms, 500 rows (431.6x). Per-item SaveChanges is the current RefreshMetadata shape on the External DB; the batched variant saves once per media type.
- **contention**: DELETE + busy_timeout 0 (current) 67011.5 ms, 797 rows -> WAL + busy_timeout 5000 (proposed) 3039.0 ms, 800 rows (22.1x). Same parallel-writer workload under the current config vs WAL + busy_timeout 5000. The busy count, not just the time, is the headline: a busy error in production is a failed save or a swallowed update (cf. PR #5458).
- **lookup**: no index (current) 610.1 ms, 1000 rows -> indexed TheMovieDbId 46.0 ms, 1000 rows (13.3x). Point lookups by TheMovieDbId over 20,000 content rows, with and without an index on the lookup key. Current snapshots do not index these keys.

Reproduce: `dotnet run -c Release --project benchmarks/Ombi.SqliteBenchmarks` from the repo root.
