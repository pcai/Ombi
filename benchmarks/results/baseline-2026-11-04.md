# Ombi SQLite benchmark results

Run: 2026-11-04 15:14:11 UTC. Host: Ubuntu 24.04.5 LTS, X64, .NET 8.0.33. Iterations: 3 per scenario (warmup discarded, median reported).

Pattern scenarios (availability, whole-graph-update, refresh-metadata, lookup) run under a fixed pre-refactor SQLite configuration (DELETE journal, busy_timeout 0) so the pattern effect is measured separately from the configuration effect. Only `contention` compares configurations.

Absolute milliseconds on this host are inflated by slow fsync (each SQLite transaction commit costs ~80 ms on this VM's disk); the ratios between variants and the busy counts are the signal, not the absolute numbers. `Rows written` is the sum of EF Core SaveChanges return values: for whole-graph-update it shows how many rows a one-field change rewrites. These are worst-case pattern measurements, not job runtimes: the availability scenario matches all 500 movies and saves up to three times per movie (the real code saved at most twice, and only for matched movies); refresh-metadata excludes the network lookups the real job performs; and the contention pair mixes WAL with the per-commit fsync drop from synchronous NORMAL (which survives a process crash but can lose the last transactions on OS crash or power loss). Ratios vary by host (the lookup pair measured 13.3x on Linux and 3.7x on Windows), so compare runs on the same host; the Host line above records this run's host.

## Reading the pairs

- **availability**: per-item SaveChanges (pre-refactor Plex shape) 132309.3 ms, 1500 rows -> one SaveChanges at end 119.5 ms, 500 rows (1107.4x). Per-item SaveChanges was the PlexAvailabilityChecker shape before batching; the batched variant is the shape all three availability checkers now use (mutate in loop, one save at end).
- **whole-graph-update**: Db.Update(detached graph) 1741.4 ms, 1120 rows -> stub + IsModified on one property 1860.6 ms, 20 rows (0.9x). Db.Update on a detached TV graph is what TvRequestRepository.Update does for detached callers; the stub variant marks only the changed property, as MarkAsAvailable already does in-repo.
- **refresh-metadata**: SaveChanges per item (pre-refactor) 45278.8 ms, 500 rows -> one SaveChanges at end 116.0 ms, 500 rows (390.3x). Per-item SaveChanges was the RefreshMetadata shape on the External DB; the batched variant saves every 100 items plus a final save per pass.
- **contention**: DELETE + busy_timeout 0 (pre-refactor) 67170.3 ms, 797 rows -> WAL + busy_timeout 5000 + synchronous NORMAL 3035.1 ms, 800 rows (22.1x). Same parallel-writer workload under the pre-refactor config vs WAL + busy_timeout 5000 + synchronous NORMAL. The busy count, not just the time, is the headline: a busy error in production is a failed save or a swallowed update (cf. PR #5458).
- **lookup**: no index (pre-refactor) 547.2 ms, 1000 rows -> indexed TheMovieDbId 47.4 ms, 1000 rows (11.5x). Point lookups by TheMovieDbId over 20,000 content rows, with and without an index on the lookup key. The indexed variant is the shape the lookup-index migration provides.

Reproduce: `dotnet run -c Release --project benchmarks/Ombi.SqliteBenchmarks` from the repo root.
